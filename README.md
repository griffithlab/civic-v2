# CIViC: Clinical Interpretations of Variants in Cancer

CIViC is an open access, open source, community-driven web resource for Clinical Interpretation of Variants in Cancer, available online at [civicdb.org](https://civicdb.org/). Our goal is to enable precision medicine by providing an educational forum for dissemination of knowledge and active discussion of the clinical significance of cancer genome alterations. For more details and to cite CIViC please refer to [the CIViC publication in Nature Genetics](http://www.nature.com/ng/journal/v49/n2/full/ng.3774.html).

## Description

The CIViC knowledgebase project seeks to advance cancer precision medicine with community collaboration. Precision medicine refers to the use of prevention and treatment strategies that are tailored to the unique features of each individual and their disease. In the context of cancer this might involve the identification of specific mutations shown to predict response to a targeted therapy. The biomedical literature describing these associations is large and growing rapidly. Currently these interpretations exist largely in private or encumbered databases resulting in extensive repetition of effort. Realizing precision medicine will require this information to be centralized, debated, and interpreted for application in the clinic.

All content created in CIViC is, and will continue to be, freely available, without restriction with a Public Domain License. Anyone can contribute to CIViC by simply registering for an account. Users join the community with “Curator” level privileges that allow them to comment or propose additions or revisions on any knowledge in CIViC. Proposed additions and revisions are then reviewed by users with “Editor” level privileges before gaining “Accepted” status. Submitted content, not yet accepted, should be interpreted/used with caution. Community Curators work together with Editors towards comprehensive and accurate interpretations of the clinical relevance of variants in cancer.

## Architecture

CIViC is a two-part application in a single repository:

- **`server/`** — a Ruby on Rails 8 application serving a GraphQL API (graphql-ruby), backed by PostgreSQL. Background jobs run on Sidekiq (Redis), and search is provided by Elasticsearch via Searchkick. In production the Rails app also serves the compiled frontend from `server/public/`.
- **`client/`** — an Angular 22 single-page application using [ng-zorro-antd](https://ng.ant.design/) components, [Apollo Client](https://www.apollographql.com/docs/) / apollo-angular for GraphQL, and [ngx-formly](https://formly.dev/) for forms. TypeScript types and Apollo services are generated from the server's GraphQL schema with [GraphQL Code Generator](https://the-guild.dev/graphql/codegen).

The same GraphQL API that powers the frontend is available for anyone to use. The easiest way to get started is to experiment in the [GraphiQL user interface](https://civicdb.org/api/graphiql). Autogenerated API documentation is available [here](https://griffithlab.github.io/civic-v2/), and example API scripts (Python, R, Ruby) live in [`examples/`](examples/).

## Getting Started

### Dependencies

- **Ruby 4.0** (see `server/.ruby-version`; install via your preferred version manager — rbenv, proto, etc.)
- **PostgreSQL >= 14** with the [pgvector](https://github.com/pgvector/pgvector) extension (CI runs Postgres 18)
- **Elasticsearch 7.x** (search indexing via Searchkick)
- **Redis** (Sidekiq background jobs)
- **Node.js >= 22** (CI runs Node 24)
- **Yarn 4** (managed via Corepack — `corepack enable` is all you need; the exact version is pinned in `client/package.json`)

### Backend setup

In `server/`:

```sh
gem install bundler
bundle install
rails db:create
rails db:schema:load
rails s   # API server at http://localhost:3000
```

See [`server/README.md`](server/README.md) for details on background jobs, GraphQL schema dumps, and testing.

### Frontend setup

In `client/`:

```sh
corepack enable
yarn install
yarn start   # dev server at http://127.0.0.1:4200, proxies API requests to :3000
```

The dev server proxies `/api`, auth, and related routes to the Rails backend on port 3000 (see `client/proxy.config.json`), so run both together for full functionality. See [`client/README.md`](client/README.md) for the full script reference, including the GraphQL code generation workflow.

### GraphQL schema & codegen workflow

The client's generated types are derived from a schema dump produced by the server. After changing the server's GraphQL schema:

```sh
# in server/
bundle exec rails graphql:schema:dump   # writes to client/src/app/generated/

# in client/
yarn generate-apollo                    # regenerate types & Apollo services
```

During active development, `yarn generate-apollo:start` watches `.gql` documents and regenerates on change.

## Development

### Backend linting & security

The Rails application uses `rubocop` for linting/formatting and `brakeman` for vulnerability scanning; both run in CI.

In the server directory you can run `./bin/rubocop -a` to autocorrect formatting issues before pushing. To run it automatically, set up the [pre-commit](https://pre-commit.com) framework, use an editor integration such as [conform.nvim](https://github.com/stevearc/conform.nvim) or [vscode-rubocop](https://github.com/rubocop/vscode-rubocop), or copy the sample hook at `server/.pre-commit-sample` into `.git/hooks/pre-commit`.

If CI fails with a `brakeman` warning that is a false positive, run `./bin/brakeman -I` from `server/`, review each warning, and add a note explaining why it should be skipped; this updates `config/brakeman.ignore`, which you can commit.

### Frontend linting & formatting

The client uses ESLint (`yarn lint`) and Prettier. Run `yarn prettier --write <files>` on touched files before committing.

### Testing

- **Backend:** `bundle exec rails test` from `server/` (Minitest; requires a test database and Elasticsearch).
- **Frontend:** `yarn test` from `client/` (Vitest via the Angular CLI; smoke tests cover app bootstrap and route rendering).

### git blame

To exclude the bulk linting/formatting commits from `git blame`, run from the project root:

```sh
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

## Continuous Integration

GitHub Actions workflows (`.github/workflows/`) run on pull requests and pushes:

- **Tests** — Brakeman scan, Rubocop lint, backend Minitest suite (Postgres + Elasticsearch services), and frontend Vitest suite + production build.
- **Build Frontend / Deploy / Staging** — build and deployment pipelines.
- **Docs** — publishes GraphQL API documentation to GitHub Pages.
